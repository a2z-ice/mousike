Quick Diagnostics Checklist

Run these commands first to get a snapshot of system health. Most issues can be identified from this checklist alone.

30-Second Health Check

# 1. Are all pods running?
kubectl get pods -n rag

# 2. Is the app healthy?
curl -s http://localhost:8080/actuator/health | python3 -m json.tool

# 3. Is Ollama responding?
curl -s http://localhost:11434/api/tags | python3 -m json.tool

# 4. Is document-service healthy?
curl -s http://localhost:8091/actuator/health | python3 -m json.tool

Docker Desktop Not Running ERROR

Symptom: docker: command not found or Cannot connect to the Docker daemon

Expected
$ docker info
Server Version: 27.x.x
...
Actual
$ docker info
ERROR: Cannot connect to the Docker daemon at unix:///var/run/docker.sock.
Is the docker daemon running?

Fix:

  1. Open Docker Desktop application manually
  2. Wait for the whale icon in the menu bar to stop animating
  3. Verify: docker info should show server version
Docker Desktop 500 Internal Server Error WARNING

Symptom: docker info returns but docker ps gives 500 Internal Server Error. Docker is in a zombie state.

$ docker ps
Error response from daemon: 500 Internal Server Error

Root Cause: Docker Desktop process crashed but socket file remains. Common after macOS sleep/wake cycles.

Fix:

# Force quit Docker Desktop
osascript -e 'quit app "Docker"' 2>/dev/null
sleep 5
pkill -f "Docker Desktop" 2>/dev/null

# Wait 10 seconds, then restart
open -a "Docker"

# Wait for Docker to fully start (30-60 seconds)
while ! docker info &>/dev/null; do sleep 3; done
echo "Docker is ready"

Kubernetes Pod Issues

Pod Stuck in Init:0/2 ERROR

Symptom: Pod shows Init:0/2 and never becomes Ready.

Root Cause: Init containers wait indefinitely for dependencies (postgres, redis, docling). If those services aren't running, the pod will never start.

# See which init container is stuck
kubectl describe pod <pod-name> -n rag | grep -A 5 "Init Containers"

# Check init container logs
kubectl logs <pod-name> -n rag -c wait-for-postgres
kubectl logs <pod-name> -n rag -c wait-for-redis
kubectl logs <pod-name> -n rag -c wait-for-docling

Init Container Dependencies

PodWaits ForCheck MethodTypical Wait
mousikepostgres (TCP 5432), redis (TCP 6379)netcat (nc -z)30-60s
document-servicepostgres (TCP 5432), docling (HTTP /health)netcat + wget60-300s (docling is slow)
ingester jobpostgres, docling, redisnetcat + wget60-300s

Fix: Ensure the dependency pods are running first. Docling is the slowest — it downloads ML models on first boot (up to 5 minutes).

# Get the crash reason

HikariCP Connection Pool Exhausted WARNING

Symptom: Requests hang, then fail with HikariPool-1 - Connection is not available, request timed out after 10000ms

Root Cause: All 10 connections in the pool are in use (slow queries, connection leaks, or high concurrency).

Configuration:

# From application.yml
spring.datasource.hikari:
  connection-timeout: 10000   # 10s wait for connection
  maximum-pool-size: 10       # Max 10 simultaneous connections

Fix: Check for slow queries in PostgreSQL logs, or increase pool size if legitimate high load.

PGVector Dimension Mismatch ERROR

Symptom: Embedding insertion fails with expected 768 dimensions, not XXX

Root Cause: The nomic-embed-text model produces 768-dimensional vectors. If you switch models, the dimensions may differ.

# Check current vector table dimensions
kubectl exec postgres-0 -n rag -- psql -U mousike -c \
  "SELECT column_name, udt_name FROM information_schema.columns WHERE table_name='vector_store';"

# Configuration expects 768 dimensions:
# spring.ai.vectorstore.pgvector.dimensions: 768

# If dimension mismatch, you must drop and recreate the vector table:
kubectl exec postgres-0 -n rag -- psql -U mousike -c "DROP TABLE IF EXISTS vector_store CASCADE;"
# Then restart the app (ddl-auto: update will recreate it)
Schema Auto-Update Failures WARNING

Configuration: spring.jpa.hibernate.ddl-auto: update

Hibernate's update mode can add columns/tables but cannot:

  • Drop columns or tables
  • Change column types
  • Rename columns
  • Alter constraints

If you change entity classes in incompatible ways, you must manually alter the database or drop/recreate.

Vector Store Query Issues

Search Returns Empty Results INFO

Symptom: GET /api/search?q=beethoven returns [] even though documents were ingested.

Root Causes:

  • Similarity threshold too high: The search uses similarityThreshold(0.6). If vectors are not close enough, results are filtered out.
  • Documents not ingested: The ingestion job may not have run or may have failed.
  • Category filter mismatch: If you pass &category=wrong_category, the filter expression returns nothing.
  • Embedding model mismatch: Documents were embedded with a different model than queries.
# Check how many vectors are in the store
kubectl exec postgres-0 -n rag -- psql -U mousike -c "SELECT count(*) FROM vector_store;"

# Check document metadata
kubectl exec postgres-0 -n rag -- psql -U mousike -c \
  "SELECT metadata->>'category' as cat, count(*) FROM vector_store GROUP BY cat;"

# Test raw similarity search
kubectl exec postgres-0 -n rag -- psql -U mousike -c \
  "SELECT content, metadata FROM vector_store LIMIT 5;"
Understanding Similarity Thresholds INFO

The system uses two different similarity thresholds in different contexts:

ContextThresholdWhere SetPurpose
Semantic Search API0.60SemanticSearchService.javaFilter results for /api/search endpoint
RAG Retrieval Gate0.65RagRetrievalGate.javaGate check before LLM call — higher bar for RAG
ChatClient RAG Advisor0.50AiConfig.javaQuestionAnswerAdvisor default threshold

If a query gets search results but RAG says "I don't have enough information", the results passed the 0.50 threshold but not the 0.65 gate.

Model Issues

LLM Response is Slow (>30 seconds) WARNING

Root Causes:

  • First request after model load: Ollama loads the model into memory on first use. This can take 10-30 seconds.
  • Model unloaded: Ollama unloads models after inactivity. Subsequent requests re-load.
  • Insufficient RAM: llama3.2 needs ~4GB RAM. If the system is swapping, it will be very slow.
  • No GPU acceleration: CPU-only inference is 5-10x slower than GPU.

Configuration that affects speed:

# From application.yml
spring.ai.ollama.chat.options:
  temperature: 0.7     # Higher = more random, slightly slower
  top-p: 0.9           # Nucleus sampling parameter
  num-ctx: 4096        # Context window — larger = more memory needed
LLM Output is Garbage / Wrong Format WARNING

Symptom: Classification returns free text instead of structured JSON. Extraction returns incomplete data.

Root Cause: Small local models (like llama3.2 at 3B parameters) are less reliable at structured output than large cloud models (GPT-4, Claude).

Mitigation:

  • Lower temperature to 0.3 for structured tasks (classification, extraction)
  • The system includes output validation (OutputValidator) that checks grounding ratio — if below 30%, the response is rejected
  • Retry the request — local models have higher variance

Context Window Limits

Context Window Overflow INFO

Configuration: num-ctx: 4096 tokens (roughly 3000 words)

What counts toward the context window:

  • System prompt
  • Chat memory (up to 20 messages from the MessageWindowChatMemory)
  • Retrieved RAG documents (can be 5 chunks × 500+ words each)
  • The user's current question
  • The model's response

Symptom when exceeded: Ollama silently truncates the input. The model may "forget" earlier parts of the conversation or ignore retrieved documents.

Mitigation:

  • Chat memory is windowed to 20 messages — older messages are automatically dropped
  • RAG retrieves max 5 documents (topK: 5) to limit context usage
  • If needed, increase num-ctx to 8192 (will use more memory)

# From host:

# From inside the mousike pod:

# spring.ai.mcp.client.sse.connections.document-service.url: http://localhost:8090/mcp/sse

MCP Protocol Detail INFO

MCP uses HTTP + Server-Sent Events (SSE) transport. The client opens an SSE connection to /mcp/sse, and the server pushes tool call results back through this channel.

Configuration:

# Client side (mousike application.yml)
spring.ai.mcp.client:
  enabled: true
  name: mousike-mcp-client
  version: "1.0.0"
  request-timeout: 30s       # ← Tool call timeout
  type: SYNC                  # Synchronous mode
  sse:
    connections:
      document-service:
        url: http://localhost:8090/mcp/sse   # SSE endpoint

# Server side (document-service application.yml)
spring.ai.mcp.server:
  enabled: true
  name: document-service
  version: "1.0.0"

MCP Tool Call Issues

Tool Returns "No relevant music knowledge found" WARNING

Symptom: Agentic RAG returns an answer like "I couldn't find relevant information" even though documents exist.

Root Cause: The MCP tool searchMusicKnowledge performs a vector search with a minimum score filter. If the score is set too high or the query doesn't match, it returns no results.

Available MCP Tools (registered by document-service):

Tool NameParametersReturnsFailure Response
searchMusicKnowledge query (string), topK (int, default 5), minScore (double, default 0.5) Matched document chunks with scores "No relevant music knowledge found for query: X"
searchByCategory query (string), category (string), topK (int, default 5) Category-filtered document chunks "No results found for 'X' in category 'Y'"
listAvailableDocuments (none) Static list of available document categories Never fails (returns static data)
Ollama Doesn't Call MCP Tools WARNING

Symptom: Agentic RAG gives a generic answer without using tools. The LLM answered from its training data instead of calling MCP tools.

Root Cause: Small local models like llama3.2 are less reliable at function/tool calling compared to larger models. The model may not recognize when to use a tool.

What to check:

  • Look at Phoenix traces — did the LLM's response include a tool call?
  • The system prompt should instruct the model to use tools for music-related questions
  • Try rephrasing the question to be more explicit about needing document search

SSE Transport Issues

SSE Connection Drops WARNING

Symptom: Agentic RAG works intermittently — sometimes tools return results, sometimes they timeout.

Root Cause: The SSE (Server-Sent Events) connection between MCP client and server can be interrupted by:

  • Network timeouts (Kubernetes service mesh, DNS resolution delays)
  • Pod restarts during a request
  • Load balancer idle timeout (if any proxy is between services)

Debugging:

# Check if SSE endpoint is accessible
curl -N -H "Accept: text/event-stream" http://localhost:8091/mcp/sse

# Should see SSE events streaming (headers then event data)
# Ctrl+C to stop

# Check mousike logs for MCP errors
kubectl logs -l app=mousike -n rag | grep -i "mcp\|sse\|tool"

MCP Timeouts

MCP Request Timeout (30s) ERROR

Symptom: Agentic RAG takes exactly 30 seconds then returns an error or empty response.

Root Cause: The MCP client has a 30-second timeout (spring.ai.mcp.client.request-timeout: 30s). If the document-service takes longer (e.g., Ollama is slow at generating embeddings for the search query), the call times out.

Chain of latency:

MCP Tool Call → document-service receives request
  → VectorStore.similaritySearch()
    → Ollama nomic-embed-text (embed the query)      ← Can be 5-10s on CPU
    → PostgreSQL PGVector HNSW search                 ← Usually <100ms
  → Format results and return via SSE                 ← <10ms

Total: If embedding takes >25s → timeout!

Fix: Ensure Ollama has the embedding model loaded. The first embedding call after model load is slowest.

RAG: No Results / Empty Answers

RAG Returns "I don't have enough information" ERROR

This is the expected behavior of the anti-hallucination guardrails when the system cannot find relevant documents. But if it happens for questions that should have answers:

Guardrail Pipeline (3-Layer Defense)

User Question │ ▼ ┌─────────────────────────────────────────────────┐ │ LAYER 1: Retrieval Gate (RagRetrievalGate) │ │ │ │ 1. Search PGVector with threshold 0.65 │ │ 2. Check: candidates.isEmpty()? │ │ YES → Return: "I don't have enough info" │ │ 3. Check: candidates.size() < 2? │ │ YES → Return: "I don't have enough info" │ │ (Only 1 chunk = low confidence) │ │ │ │ PASS → Continue to LLM │ └────────────────────┬────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────┐ │ LAYER 2: System Prompt │ │ │ │ LLM instructed: "If the provided context │ │ does not contain enough information to │ │ answer, say so. Never make up facts." │ │ │ │ LLM generates answer... │ └────────────────────┬────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────┐ │ LAYER 3: Output Validator (OutputValidator) │ │ │ │ 1. Check: response empty/null? │ │ YES → Block: "Empty response from LLM" │ │ 2. Check: retrieved chunks empty? │ │ YES → Block: "No retrieved chunks" │ │ 3. Calculate grounding ratio: │ │ groundedWords / contentWords │ │ Ratio < 0.30? → Block: "Low grounding" │ │ (Words <4 chars are skipped) │ │ │ │ PASS → Return answer to user │ └─────────────────────────────────────────────────┘

Diagnostic steps:

  1. Check if documents are ingested: kubectl exec postgres-0 -n rag -- psql -U mousike -c "SELECT count(*) FROM vector_store;"
  2. Check if search returns results: curl "http://localhost:8080/api/search?q=YOUR_QUERY&topK=5"
  3. Check Phoenix traces to see which guardrail layer blocked the response
  4. If search returns results but RAG doesn't, the similarity threshold (0.65 for RAG vs 0.60 for search) may be the difference

Hallucination Detection

Output Validator: Low Grounding Ratio ERROR

What it means: The OutputValidator checks what percentage of the LLM's response words appear in the retrieved context. If less than 30% of words are grounded in the source material, the response is rejected.

How grounding is calculated:

// OutputValidator.java (simplified)
for each word in LLM_response:
    if word.length >= 4:                    // Skip short words (a, the, is, etc.)
        contentWords++
        if word appears in retrieved_chunks:
            groundedWords++

groundingRatio = groundedWords / contentWords
if groundingRatio < 0.30:
    REJECT → "Low grounding ratio: 0.XX"

When this triggers incorrectly:

  • The LLM paraphrases the source material heavily (uses synonyms instead of exact words)
  • The LLM adds legitimate explanatory text that isn't in the source
  • The source material uses technical abbreviations but the LLM spells them out

Guardrail Failures

Guardrails Pass When They Shouldn't WARNING

Symptom: The system answers questions with hallucinated data despite guardrails.

Possible causes:

  • Documents are too generic: If the vector store contains broad documents, the similarity search may return results even for off-topic queries (0.65 threshold met)
  • Minimum chunk count met: The gate requires at least 2 chunks. If 2+ low-quality chunks match, the gate passes
  • Grounding ratio is high enough: If the hallucinated answer happens to share many words with the context (e.g., common music terminology), the 30% threshold passes

Mitigation: Increase similarity threshold, increase minimum chunk count, or increase grounding ratio threshold.

Chat Memory Issues

Chat Doesn't Remember Previous Messages ERROR

Symptom: You tell the chatbot your name, then ask "What is my name?" and it doesn't know.

Root Causes:

  • Different conversationId: Each conversation is identified by a UUID. If you don't send the same conversationId, it's a new conversation.
  • Memory window exceeded: Only the last 20 messages are kept. Older messages are dropped.
  • Database failure: If PostgreSQL is down, memory operations fail (500 error).
# Test memory persistence

# Step 2: Ask about the name (same conversationId!)
curl -s -X POST http://localhost:8080/api/chat \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"What is my name?\", \"conversationId\":\"$CONV_ID\"}" | python3 -m json.tool

# Expected: Response should mention "TestBot"

# Step 3: Clear memory
curl -s -X DELETE "http://localhost:8080/api/chat/$CONV_ID"

Chat Response Stops Mid-Stream WARNING

Symptom: The chat response starts appearing but stops partway through, leaving an incomplete message.

Root Cause: The Vaadin ChatView uses reactive streaming (Flux) to display tokens as they arrive from Ollama. If the stream breaks mid-response:

  • Ollama process crashed or ran out of memory
  • Network interruption between pod and Ollama
  • User navigated away (the getUI() returns empty, updates silently ignored)

Note: The ChatView does not have an error handler on the reactive stream. Errors are silently swallowed — no error message is shown to the user.

// ChatView.java — no error handling on subscribe()
chatService.chat(conversationId, message)
    .doOnNext(token -> {
        responseBuilder.append(token);
        getUI().ifPresent(ui -> ui.access(() ->
            responseBubble.setText(responseBuilder.toString())));
    })
    .subscribe();  // ← No .doOnError() handler!

Application Startup Failures

Application Fails to Start ERROR

Symptom: Pod in CrashLoopBackOff. Logs show Spring Boot startup failure.

Common startup errors:

Database Connection Error 
org.postgresql.util.PSQLException: Connection to localhost:5432 refused.
Check that the hostname and port are correct and that the postmaster is accepting connections.

Fix: Ensure PostgreSQL pod is running. In K8s, the init container should wait for it, but if the init container is misconfigured, the app may start before PostgreSQL is ready.

Chat Memory Schema Error 
org.springframework.jdbc.BadSqlGrammarException:
  Table 'ai_chat_memory' doesn't exist

Fix: Verify spring.ai.chat.memory.repository.jdbc.initialize-schema: always is set. If using a custom schema, ensure the schema name matches.

PGVector Extension Missing 
org.postgresql.util.PSQLException: ERROR: type "vector" does not exist

Fix: The PostgreSQL image must be ankane/pgvector:latest (not regular postgres). Check: kubectl exec postgres-0 -n rag -- psql -U mousike -c "CREATE EXTENSION IF NOT EXISTS vector;"

MCP Client Connection Error on Startup 
Failed to establish SSE connection to http://document-service:8090/mcp/sse

Fix: The document-service must be running before mousike starts. This is not enforced by init containers (mousike only waits for postgres and redis). If document-service is slow, restart mousike pod after document-service is ready.

Port Already In Use (Local Development) 
Web server failed to start. Port 8080 was already in use.

Fix: Another process (or Kind port forward) is using port 8080. Check: lsof -i :8080

Trace: POST /api/chat

├── ChatClient.call() with QA advisor     [~5-25s]
│   └── OllamaChatModel.call()            [~5-25s]

Image Loading Issues

Images Not Found in Kind ERROR

Symptom: ErrImageNeverPull or ImagePullBackOff after deploying.

Root Cause: All custom images use imagePullPolicy: Never — they must be pre-loaded into Kind. Kind nodes are separate Docker environments; images on the host are NOT automatically available.

# Step 1: Verify images exist locally
docker images | grep -E "mousike-app|document-service"

# Step 2: Load into Kind
kind load docker-image mousike-app:latest --name mousike-cluster
kind load docker-image document-service:latest --name mousike-cluster

# Step 3: Verify images are in Kind
docker exec mousike-cluster-control-plane crictl images | grep -E "mousike|document"

# Step 4: Restart deployments to pick up new images
kubectl rollout restart deployment/mousike -n rag
kubectl rollout restart deployment/document-service -n rag

Common mistake: Using --skip-build with start-stack.sh after recreating the Kind cluster. The cluster is fresh but images weren't reloaded. The script handles this correctly, but if you're deploying manually, always run kind load after creating a new cluster.

Nuclear Option: Complete Restart

When Nothing Else Works INFO

If you've exhausted all other options, here's how to start completely fresh:

  1. Stop everything: ./scripts/stop-stack.sh --clean --yes
  2. Verify Docker Desktop is running and healthy: docker info
  3. Verify Ollama is running: curl http://localhost:11434/api/tags
  4. Pull required models: ollama pull llama3.2 && ollama pull nomic-embed-text
  5. Start fresh: ./scripts/start-stack.sh
  6. Wait for all sanity tests to pass (15/15)
  7. Verify with: kubectl get pods -n rag — all should be 1/1 Running

Total time from clean start: 15-30 minutes (depending on network speed for image pulls and model downloads).
